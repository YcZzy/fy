## 2. 产品需求是否合理

### 有价值、应保留的部分

**核心问题具体。** 用户拥有一段空闲，却不知道做什么；时间、精力、环境三个条件能有效缩小选择范围。“此刻”的任务比泛化待办工具更明确。

**允许休息、娱乐、部分完成的定位自洽。** 不做排名、完成率和惩罚性提醒，适合想降低自我管理压力的人。完成状态、感受和回顾可以服务于自我理解。

**三个主页面具有时间逻辑。** “此刻”负责当下选择，“风月”承载长期想法，“足迹”保存已经发生的经历。暖杏、蓝灰、鼠尾草绿的主题区分也有一致性。

**AI 有人工确认与本地降级。** 推荐失败仍可走规则推荐；行动和计划草稿需要用户确认。照片和位置是选填项，这些方向正确。

### 目前没有完全想清楚的需求

| 问题 | 当前表现 | 判断与建议 |
| --- | --- | --- |
| 主要用户到底是谁 | 同时覆盖休息、考公、英语、旅行、聊天和日记 | 广泛生活场景可以存在，但首版应明确主要服务“空闲不知道做什么”的人；计划和 AI 对话为这条主线服务 |
| 低负担如何衡量 | 四步引导、多个筛选、大量卡片、较长记录表单 | 把“从进入到决定做什么”“从结束到完成记录”的操作步骤作为验收对象；用用户测试确定时长目标 |
| 是否必须每次五个推荐 | AI 不足五个就整体降级；规则推荐可能少于五个 | 五个不是天然正确的数量。更合理的是优先展示少量高匹配结果，明确允许结果不足，并提供调整条件 |
| “计划”的边界 | 无截止压力，却有状态、关注、板块、关联、日期、回顾 | 可以定义为“长期体验主题”，不必补进度条；但需要明确与愿望、行动的区别 |
| 板块是否必须限制关联 | 计划和行动必须同板块 | 分类硬约束过强。例如“周末城市探索”可以同时包含旅行、散步和摄影。建议板块用于分类，关联由用户意图决定；若坚持单板块，需在产品中解释 |
| “没有去做”是什么数据 | 可以保存，但回顾把它当作出现过的行动 | 可以保留“选择记录”，但必须与“实际参与”分开统计，AI 也必须知道完成状态 |
| 收集“以后还想做吗”有何作用 | `doAgain` 只保存和回显，推荐和回顾未使用 | 属于没有形成反馈回路的字段；要么接入用户可理解的偏好调整，要么暂时移除以减轻表单 |
| 使用位置为了什么 | 位置和“在家/通勤”占据同一个环境字段 | 物理情境与地理区域应分开；北京并不能说明用户在户外。若仅给泛活动类别，定位带来的收益需要说明 |
| “结束提醒”承诺什么 | 只在部分页面检查到期，开始后才弹出限制说明 | 应在点击前说明“停留此页或返回此刻时提醒”；只有具备对应能力后才使用更宽泛的提醒文案 |

不建议为“完善”而增加社区、排行榜、打卡、成长分或复杂项目管理。当前更需要把已经承诺的流程做稳。

## 3. 核心流程完整性

| 用户目标 | 当前路径 | 主要断点 |
| --- | --- | --- |
| 新用户找到第一件事 | 首次引导 → 兴趣 → 愿望 → 初始行动 → 此刻 → 筛选 → 推荐 → 行动详情 → 开始 | 引导没有上一步；默认生成个人计划和愿望；第一件事之前的操作较多 |
| 快速开始已有行动 | 风月 → 向下找行动库 → 展开 → 点击行动 → 详情 → 开始 | 行动库位置深；“最近关注”和全部计划重复占据前部空间 |
| 按计划行动并回看 | 新建计划 → 保存返回 → 重新进入 → 关联行动 → 保存 → 去别处开始 | 新计划不能在同一创建流程中安排下一步；计划详情没有已接通的“开始行动”按钮 |
| 不计时，直接去做 | 行动详情 → 直接去做 → 返回 → 离开小程序 → 一分钟后再回此刻 → 追问 | 待记录卡片缺失；取消追问会消耗唯一追问；第二个直接行动覆盖第一个 |
| 计时并记录 | 开始 → 暂停/恢复 → 结束并记录 → 保存 → 足迹 | 暂停不延后提醒；进入记录页没有冻结会话；编辑旧足迹还会清掉当前计时 |
| 回顾实际生活 | 足迹 → 回望 → 选择周期 → 生成 → 保存 | 未做的行动与已做混合；未知时长变成零；保存的回顾没有具体日期区间 |
| 用 AI 展开想法 | 问风月 → 提问 → 草稿 → 确认/修改 → 保存 | 保存草稿丢字段；修改草稿前就清除当前草稿；缺少保存后直达行动/计划 |
| 换设备继续使用 | 新设备初始化 → 引导 → 页面拉云数据 | 默认偏好时间更新，可能压过云端偏好；对话没有正常入口主动拉取云端历史 |
| 删除个人数据 | 两次确认 → 云端删除 → 本地重置 → 引导 | 待同步快照未取消，已删数据可以重新上传和恢复 |

这里最需要解决的不是页面数量，而是同一件事在页面间是否保留了身份、状态和上下文。

## 5. 全部页面：内容、交互与布局

### 5.1 首次引导

**已有：** 定位说明、兴趣多选、自定义兴趣、模糊愿望、初始行动编辑与移除。

**缺口：** 只有继续和跳过，没有上一步；输入的自定义兴趣需额外点“加入”，否则不进入选择结果；兴趣后续没有修改入口。四步是否能“一分钟完成”没有测试依据。

**内容不真实：** 初始状态直接创建“六周英语体验”“北京街区探索”和一条愿望，包含关注状态和过去日期，未标为示例。用户未选择这些内容，却会在“我的计划”和首页出现。预置公共行动库合理，预置个人经历式数据不合理。应使用可选示例或空状态。[默认数据](C:/Users/LEGION/Desktop/fy/miniprogram/data/defaults.js:31)

**布局建议：** 保留品牌气质，压缩首段留白；优先让用户快速进入第一轮推荐。兴趣和行动调整可以后补。自定义导航只处理了安全区顶部，没有显式处理右上角微信胶囊避让；需真机检查顶部“跳过”的位置。

### 5.2 此刻

**已有：** 时间、精力、环境、自由描述、关注计划行动、推荐、计时入口、聊天和设置。

**明确缺少的内容：** 自定义时间没有显示实际选中的数值；选择地点后没有显示 `locationSummary`；未找到推荐时整个结果区隐藏，用户看不到“没有匹配结果”及下一步操作；待直接行动没有可见入口。

**交互问题：** “暂时不想做”会换整组，不只处理这一项；“换个类似的”通常受默认库规模限制；“就做这个”与“开始这个行动”实际上先进入详情，文案应让用户预期一致。只在 `onShow` 检查首页的提醒，留在此刻页到时不会由首页 ticker 发出同样提醒。

**布局判断：** 核心状态表单位于关注卡片之后，推荐结果又在表单之后；已有五项结果时聊天入口非常靠后。首屏应突出当前待办状态与选择入口，关注行动压缩为次级内容。生成后可滚动到结果区域并给出明确反馈。

### 5.3 风月

**已有：** 关注计划、状态筛选、计划列表、愿望、板块、可搜索行动库、AI 入口。

**主要问题：** 一个页面承担六类内容；关注计划与计划列表有重复；八个板块占四行，行动库还在其后且默认收起。点击板块只在下方筛选行动，没有跳到结果或局部反馈，用户可能误以为没反应。

**内容缺口：** 愿望没有编辑；计划没有删除；没有全局计划搜索。筛选“已结束”为空时仍用“这里还没有计划”，没有说明只是当前分类为空。

**建议：** 保留三个主导航，在“风月”内部用“计划 / 想做 / 行动库”清楚切换；生活板块成为筛选条件。“新行动”不要藏在长页面底部的折叠内容里。少量数据可用当前列表，较多数据需要搜索和分段加载。

### 5.4 计划详情与创建

**已有：** 名称、原因、状态、关注、板块、日期、关联行动、统计、最近足迹和反思。

**关键断点：** 新建时关联行动区全部隐藏；保存后返回列表，需再次进入才能安排下一步。已有计划的行动行点击只切换“加入/已加入”，没有开始入口；JS 虽然定义 `openAction()`，WXML 没有绑定它。[计划关联区域](C:/Users/LEGION/Desktop/fy/miniprogram/pages/plan/index.wxml:22)

**保存不一致：** 关联切换只保存在页面内，而保存按钮位于关联区域上方；点击新行动、编辑行动、请风月想下一步、保存反思又会顺带保存整份计划。用户难判断什么时候已经保存、返回会丢什么。建议展示与编辑分开，或者统一自动保存并显示状态。

**内容缺口：** 重要日期不能清除；计划不能删除；最近足迹仅五条且不能直接编辑或查看全部相关记录；暂停计划依然可能作为关注来源推到首页，需要明确暂停语义。

**布局建议：** 详情顶部先放计划摘要与“现在做什么”，其次是已关联行动，再是经历回顾；名称、板块、状态等移入明确编辑区域。若继续表单式页面，需有稳定可见的保存入口。

### 5.5 行动编辑

**已有：** 名称、时长、精力、环境、关联计划和准备事项，主要实体字段完整。

**问题：** 没有未保存离开保护；编辑系统行动在此页不能删除，但行动库可删除同一系统行动，入口规则不一致；改变板块会移除原有关联，提示为短 toast，容易漏看。应该让关联变化明确可见。

**模型建议：** 明确“很累也能做”是独立标签还是最低精力阈值，避免用户误解必须勾全三个。创建草稿时默认精力和环境是否可信也需要提示或再次确认。

### 5.6 行动详情与计时

**已有：** 行动名称、分类、预计时间、原因、准备、计时、暂停恢复、直接去做和结束。

**问题：** 上半部分的大图形与说明占据主要空间，开始动作在下方；三个启动按钮连续排列，决策成本偏高。应突出一个主要开始动作，把计时、提醒作为明确选项。

“设置结束提醒并计时”不能让人提前知道能力边界；“稍后再说”只是返回，并未保存为稍后事项。“结束并记录”进入表单时会话仍运行，建议冻结本次时长；返回时则询问或明确恢复。

**上下文缺失：** 从行动库进入没有传 planId，详情也没有选择本次归属计划的入口。即便行动已关联计划，记录也可能不计入该计划；多计划关联时更需要用户选择，不能隐式猜测。

### 5.7 记录页

**已有：** 完成状态、实际时长、感受、文字、再做意愿、照片和位置。基础内容已经足够，不需要为了丰富继续堆字段。

**缺口：** 无主动补记入口，不能选择实际发生日期；“昨天做过但忘记记录”的需求没有顺畅路径。历史记录打开后优先使用当前行动实体，行动改名或换板块后再编辑旧足迹，存在改写旧名称/板块的风险，应优先保存历史快照。

**文案不一致：** 编辑模式仍显示“留下这次足迹”；底部写“跳过细节，直接记一笔”，但编辑模式实际只是返回。新记录的“跳过”会真的新增一条默认完成记录，不等于“不记录”。需要把“保存简略记录”“不保存退出”分开。

**位置说明不准确：** 文案说可以只保留地点名称，但实现始终存入名称、地址、经纬度，没有“仅名称”的选择器。[位置保存](C:/Users/LEGION/Desktop/fy/miniprogram/pages/record/index.js:73)

**布局建议：** 默认优先展示状态和感受，时长按入口预填；文字、照片、位置折叠为补充内容。选填不等于必须一直占据屏幕。

### 5.8 足迹与回望

**已有：** 时光列表、完成状态、图片、时长、感受、计划链接、编辑删除，以及周月年和自定义回顾。

**长期使用缺口：** 列表没有搜索、日期筛选、按计划筛选、分页或主动补记入口；图片不可点开预览。只展示月日，跨年后难以区分。

**回顾时间不明确：** 保存时有 `rangeStart/rangeEnd`，但展示仅写“本周/本月/今年/自定义”；历史几周的回顾混在同一类型下，每条都叫“本周”。自定义的多个日期范围也混在一起。即使保留全部历史，也应显示真实起止日期和生成时间。[回顾列表筛选](C:/Users/LEGION/Desktop/fy/miniprogram/pages/footprints/index.js:70)

**统计原则：** “很喜欢”不是“做过”，“没记录时长”不是零分钟，“最后没做”也不是发生过的活动。AI review 的输入没有 completionStatus，还可能把未做事项写成真实经历。先校正数据含义，再增加图表。

**布局建议：** 分离当前周期概览与历史回顾；全空时提供一个明确按钮开始/补记，避免大段零值统计与不可产生结果的生成按钮。

### 5.9 问风月

**已有：** 快捷问题、消息、草稿确认、编辑跳转、局部消息删除和最近对话。

**缺口：** 只列最近六段对话，没有全部历史或搜索；进入聊天每次新建会话，没有清楚的“新对话 / 历史对话”切换；历史删除没有确认或撤销。发送失败没有“重试这条”或“一键记到想做清单”。

**草稿生命周期不完整：** 草稿只存页面 data，未随 conversation 保存；继续发消息、重新进入、点修改后返回未保存，都可能失去草稿。确认保存后只给 toast，没有“查看计划/开始行动”。

**云恢复缺口：** 三处 `bootstrap()` 调用都不包含 conversations；chat 自身也没有拉取云对话。因此“新设备打开就看到聊天历史”的正常恢复路径缺失。之后写入对话触发推送合并可能取回数据，但不是可靠的读流程。[聊天初始化](C:/Users/LEGION/Desktop/fy/miniprogram/pages/chat/index.js:10)

**布局待测：** 输入框依赖 `100vh + flex + auto-height`，需在 iOS、Android、小屏和多行输入时验证键盘避让；消息气泡没有显式换行保留与长连续文本折行规则，多段 AI 回复可读性需测试。

### 5.10 设置与隐私

**已有：** 数据概览、权限设置、清空聊天、删除全部个人数据。

**面向用户的内容不足：** 缺少兴趣编辑、真实同步状态、最近同步时间、待同步数量、失败重试、帮助说明、版本信息和反馈入口。导出备份适合作为后续增强，至少要让用户知道本地数据是否已经备份。

**技术信息过多：** CloudBase 环境 ID 和部署术语出现在普通设置页，用户无法据此判断数据是否安全保存。“已连接”依据配置和初始化标志，并非成功读写的证明，网络失败仍可能显示已连接。[设置状态](C:/Users/LEGION/Desktop/fy/miniprogram/pages/settings/index.js:12)

隐私文字应准确说明照片、精确位置、自由文本、AI 摘要分别如何使用。当前缺少完整可查阅说明；这只是产品内容完整性发现，本报告没有作法规合规结论。

## 6. 布局与视觉的客观判断

### 已经做对的地方

主题色、圆角、卡片、按钮和辅助文字有统一规则；详情能继承入口主题。三个主页面预留了底部安全区与悬浮导航空间。不要把现有视觉体系推倒重来。

### 源码可以明确定位的问题

1. **自定义导航存在盒模型尺寸问题。** `.tab-bar` 设置宽高 100%，又增加左右 18rpx、上下 10rpx 的 padding，没有 `box-sizing: border-box`。在默认 content-box 下，实际外盒比容器宽 36rpx、高 20rpx；父级还设 `overflow: hidden`。这会使内容区域偏移并产生裁切风险，需修正后原生验证。[导航样式](C:/Users/LEGION/Desktop/fy/miniprogram/custom-tab-bar/index.wxss:39)
2. **重要状态没有视觉反馈。** 自定义分钟、选择的区域、直接行动待记录状态不在模板显示。这不是审美偏好，而是缺失了用户操作结果。
3. **按钮所在位置与操作发生位置脱节。** 计划保存按钮在关联列表前；行动库新增在长页底部折叠区；首页结果和聊天入口在长表单后。用户需要来回寻找。
4. **小操作的点击区较窄。** 首页文字按钮仅 23rpx 字号和 1.2 行高，无点击 padding；多个删除/编辑入口是小号 text。标准 375 逻辑像素宽度换算下，23rpx 约 11.5 逻辑像素，文字行高约 13.8。建议扩大触摸区域，不必同步放大所有文字。[首页次级操作](C:/Users/LEGION/Desktop/fy/miniprogram/pages/now/index.wxss:51)
5. **输入控件尺寸体系不统一。** 全局 input 使用 `2.6rem`，其他表单与 picker 多用 rpx，且 root rem 未在项目内显式统一；它未必必然错误，但跨设备一致性应收敛并验证。[全局输入样式](C:/Users/LEGION/Desktop/fy/miniprogram/app.wxss:87)

### 需要原生实测、不能现在断言错位的项目

- 首页长问候语与可收缩的设置图标；长行动名加计时数字的横向布局。
- 首次引导顶部品牌、跳过与系统胶囊的碰撞。
- 小屏上的三颗草稿按钮、记录页“以后还想再做吗”和长位置名。
- 浅色主题上的小字号辅助文案、阳光下阅读、系统字体放大后的换行。
- 键盘弹出后的聊天输入框、表单底部保存按钮，以及安全区和横竖屏行为。
- WXSS 特性、SVG 图标、玻璃效果在不同客户端的兼容与性能。全局玻璃卡片有降级样式，自定义导航没有同样的 `@supports` 降级，需要观察不支持时的可读性。

## 7. 数据、AI 与工程保障

**已有的工程基础：** 页面与服务层分开；本地优先、增量集合队列、记录合并和删除标记已存在；云函数按调用者身份查询个人文档；上传密钥走 GitHub Secret；有回归检查和自动上传流程。

**仍需补齐的部分：**

| 范围 | 源码发现 | 实际影响与建议 |
| --- | --- | --- |
| 离线照片 | 上传失败保存本地文件，同步时删除 localPhotoPaths，但没有待上传补偿流程 | 文字可以到其他设备，照片不会自动补传；增加可观察的上传队列和重试 |
| 全部删除 | 云函数主要从云端足迹读取照片 ID，未覆盖尚未同步足迹或已进本地待删除队列的所有文件 | 可能遗漏文件清理；删除协议应同时覆盖本地已知文件与云端资产，并保留失败重试信息 |
| 文件归属 | 高权限云函数使用用户可写足迹内的 photoFileIds 执行删除，未见独立文件归属核验 | 上线前专项检查文件所有权边界；本次未对真实云权限进行攻击或验证 |
| 多设备删除 | 全删是物理移除，另一设备仍可拥有旧本地数据 | 需要服务端删除代次/账户数据版本，阻止旧设备重建已删除内容 |
| 本地容量 | 每次仓储变更克隆并整体写状态；足迹、聊天逐步增长 | 当前规模未必慢，但大量记录下会增加读写和内存负担；建立容量与大数据样例验收 |
| 图片列表 | 足迹刷新先等待全部图片临时地址，再更新文字列表 | 网络慢时文字也延迟；先显示记录，再补图，并做批量、去重和分页 |
| 推荐约束 | 系统“下楼散步”标有 any，故在家/通勤也满足；手动地区没有位置模式相同过滤 | 如果环境意指“当前地点”，是否允许出门需要说明；如果意指“不能离开”，当前建议会冲突。统一语义和标签 |
| 推荐轮换 | 换组没有明确排除上一组，仅重跑分数和少量随机值 | 高分候选容易重复；加入轮换记忆、无新项说明；小库不应承诺永远有五项 |
| AI 可靠性 | 推荐有部分结构校验，聊天 draft 与 review content 校验较弱；没有应用级超时与取消管理 | 需校验类型、ID、空内容和字段长度；处理迟到、重复、失败及用户离开 |
| AI 成本规模 | 推荐发送全部可见行动，回顾发送整个周期记录，没有分批摘要或产品内预算策略 | 年度记录多时上下文增长；设置服务端调用限制、分段摘要和失败降级，实际成本需配置后测量 |
| 权限部署 | 有规则文件，但仓库本身不能证明环境已应用 | 必须做真实双用户隔离、照片访问、删除权限验证；不将“文件存在”当作“权限生效” |
| 文档准确性 | README 仍含旧的本地模式默认说明和另一台机器的绝对部署路径，实际已有 AppID/环境 | 整理为与当前配置一致的运行与部署说明，补回完整 PRD 和验收矩阵 |

现有测试通过与这些问题并不矛盾：测试主要验证正常仓储操作、推荐规则、合并和删除返回状态，未覆盖页面生命周期、异步期间用户切换、原生布局、删除全部后的队列状态和新设备首次恢复。尤其 `validate.js` 的事件扫描没有全面覆盖 catchtap 等事件，也不编译验证真实 WXML 渲染。

## 8. 建议采用的目标结构与状态规则

**此刻：** 进行中/待记录 → 精简条件 → 少量推荐 → 更多选择。关注计划行动作为快捷入口，不应压过主要选择器。结果不足时给调整条件或直接添加。

**风月：** 顶部保留“最近关注”，下方清楚区分计划、想做、行动库；行动库搜索与新建保持容易找到。板块用于筛选，避免八张大卡片长期阻断主要入口。

**足迹：** 时间列表 + 主动补记 + 日期/计划筛选；回望默认显示具体时间区间和数据说明，历史回顾单独列出真实日期。

行动过程建议统一为：未开始 → 计时中/直接进行中 → 暂停（可选）→ 待记录 → 已记录/明确放弃记录。修改历史记录不改变当前会话。每次会话有独立 ID，结束和保存按 ID 匹配。

“选择一项”“稍后”“取消”“跳过”“保存”“自动保存”的含义应全项目一致：取消不应隐式新增记录，编辑不应隐式结束别的事情，清空不应被迟到的请求撤销。

## 9. 建议执行顺序与验收条件

### 第一阶段：修正确性，再继续体验扩展

处理 R14、R01、R02、R13，以及直接行动状态、提醒暂停、推荐/回顾/聊天异步问题。补齐照片重试与云历史恢复。

验收重点：离线仍能完成主流程；改旧记录不影响当前行动；晚到请求不会覆盖新操作；删完后当前设备、重启和另一台旧设备均不能恢复旧数据；云端恢复不需要用户重新编辑一次。

### 第二阶段：让用户顺畅完成一件事

去掉未经确认的个人示例数据；精简首页与风月信息结构；补计划内开始、主动补记、历史日期、草稿保存后入口；统一所有表单保存行为和空状态。

验收重点：新用户可以找到第一项行动；用户从计划开始后能在该计划看到足迹；不计时行动回来后仍能找到；历史回顾能看懂具体对应哪段生活。

### 第三阶段：原生布局与长期使用验收

修导航盒模型与小操作点击区，整理主题和控件尺寸；在多个屏幕、字体和键盘状态下检查布局；补搜索、历史、备份/导出和可观察同步状态。

建议场景矩阵：

| 维度 | 必须覆盖的样例 |
| --- | --- |
| 用户状态 | 全新用户、跳过引导、已用一周、已有大量记录、换设备 |
| 数据量 | 0/1/5/100 个计划或行动；0/1/100/1000 条足迹与聊天的适量组合 |
| 网络 | 无云配置、离线、弱网、请求中断、恢复网络、权限拒绝 |
| 行动 | 计时、暂停很久、直接去做、返回取消追问、开始另一个、编辑旧记录 |
| 异步 | 请求过程中换条件/周期、清空、导航离开、重复点击、删除全部 |
| 页面 | 320/375/430 逻辑像素宽度代表性设备、长中文标题、连续英文、多行回复、键盘、字体放大 |
| 数据安全 | 两个账号相互隔离、照片归属、删除失败重试、重启/旧设备不会恢复已删数据 |

**当前最合理的目标，是完成一个可信、低负担的生活选择与记录闭环。功能已有较多，优先级应放在“用户看得懂、找得到、做得完、数据留得住也删得掉”。**
